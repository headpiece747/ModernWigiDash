Problem

The fetch flow is ~150 lines of widget sequence across five methods, and its one interface-level invariant — capture the identity key before the await, re-validate after — is enforced by comments only. The ADR-0006 predicate is spelled a second time inline (widget 465), and “a discarded cache load must roll the client back” is split across two modules, held together by a comment.

Solution

A WeatherFetchFlow module owns the sequence — key capture, outcome verification, guarded drop, skip mapping, write-back gating, the static-snapshot gate, the boot-load rollback — composed over the cluster’s existing seams (fetch, load, invalidate, apply). The widget keeps only gate discipline, the UI-thread flush, and the context calls.

Wins

  • ADR-0006 predicate single-spelled again
  • locality: rollback lives with its effect
  • locality: capture-window order lives in one module
  • leverage: race tests drive one flow interface
  • widget sheds ~150 sequence lines
  • deletion test: the enum was the module’s absence

Problem

Problem

The pure decision rules — coordinate parse/validate/format and the ZIP label join — sit inside the geocoding transport adapter, and the fetch-control state machine depends on the adapter’s static for a display rule. The “compose a display name from place parts” family (city ComposeLabel, ZIP join, coordinate format) has no single home; its three spellings are held apart by file placement.

Solution

Move the coordinate rules and every label composition into the WeatherLocationResolver leaf — it already owns the sibling rules and all three URL builders — leaving the geocoder a pure HTTP + parse adapter behind one interface.

Wins

  • one home for label composition
  • locality: the state machine stops crossing the seam
  • geocoder interface shrinks (4 publics go)
  • decision vs transport, finally separated

Problem

“What an invalidation drops” is spelled twice — the control’s Invalidate and the identity’s InvalidateCoordinates (keep-candidates), plus ClearCandidates / InvalidateLocation (full) — and the widget’s OnPropertyChanged pairs the twins per edit. The existing pin covers the resolution-input set, not the drop semantics. The widget-side twin is justified (different gate, UI-thread write-back); the duplicated drop rules are the trap.

Solution

Declare the drop granularity once — the same set-declaration shape WeatherQueryKey already uses for KeyPropertyNames / InvalidationProperties — with both twins consuming it, and a pin asserting the twins agree.

Wins

  • locality: a new pending state lands once
  • twin drift becomes a test failure
  • the cluster’s own pattern, reused

Noted, not scored

· The two widget render smoke tests run on an empty widget; full-data rows for the five layout modes exist only through renderer-direct models.

· LocationType is an identity dimension in WeatherQueryKey that no test varies — a single-choice property in practice.

Top recommendation

C1 — build the WeatherFetchFlow module

It is the module the cluster already named: WeatherFetchFlowOutcome documents “the verdict of one FetchLiveWeatherAsync run” while the behaviour it names sits in 150 lines of widget sequence. Deepening it absorbs the ADR-0006 residual (the second predicate spelling at widget 465), the split rollback rule (widget 664–679 ↔ client 306), the comment-only capture-window order, and gives the 1,142-line WeatherForecastWidgetTests a real interface to drive instead of widget internals. C2 falls into place behind it: once the flow module is the client’s only production caller, the capture-window knowledge sinks below the client’s surface instead of riding it.
