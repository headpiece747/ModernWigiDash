Three candidates

One owner of the stale-identity invariant

Worth exploring

Files

WeatherClient WeatherForecastWidget WeatherFetchControl WeatherCacheStore docs/adr · new ADR-0006 CONTEXT.md

Problem

The stale-identity rule is spelled out in 4-plus ways — the client's capture window, the widget's return-to-apply recheck, the cache-load comparison — and is held together by comments, with no test surface.

Solution

A single predicate over a single identity record, owned by one module and named in an ADR, so the guard is assertable in one place.

Benefit

Locality: one module carries the whole stale-identity rule. The interface is the test surface: tests pin the predicate directly over the identity record, no pixels, no fetch mocks. Leverage: every call site that re-derives the guard today routes through the one owner. The ADR names the invariant, so the next person reading the cluster knows the rule exists and where it lives.

The geocoder's two doors

Speculative

Files

WeatherClient WeatherGeocoder WeatherLocationResolver

Problem

The client reaches the location resolver through two doors — the geocoder's geocode entry point and three direct leaf calls (is-ZIP, zip-lookup URI, forecast URI) — so one decision is enforced in two places.

Solution

A single geocode-entry seam through the geocoder, with the resolver's leaf calls absorbed behind it.

Benefit

One seam, one door: the client stops building geocoding URLs and asks the geocoder the question once. The decision stays in the resolver where its rules already live. The geocoder's interface is the test surface: its entry points are the assertions, no HTTP.

Pin the identity rules of the render model

Worth exploring

Files

WeatherRenderModel.cs new WeatherRenderModelTests.cs WeatherWidgetRendererTests.cs (extend)

Problem

The identity key of the render model — the rule that decides when the cached model rebuilds — has no covering test, so a silent drift would quietly change the rebuild with nothing to catch it.

Solution

A test suite keyed on the identity record, pinning property drift, bounds drift, and the no-drift cache hit.

Benefit

The interface is the test surface: the identity record is the assertion target, no pixels involved. The cache-hit rule becomes pinned rather than presumed. Locality: the identity rule's tests live beside the key they pin.

Where to start

Card 1 — one owner of the stale-identity invariant

The stale-identity guard is the load-bearing rule the whole cluster leans on, and today it is spelled in 4-plus ways, held by comments, with no test surface and no weather ADR. Card 1 creates the single owner and the single predicate — which also shrinks the client's surface, the very surface card 2 then targets — and card 3 lands as a same-session quick win on top of it.

Cards 2 and 3 are reachable after card 1; none of them is blocked by the kept modules.
