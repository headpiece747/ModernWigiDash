# ModernWigiDash — Domain Glossary & Architecture

## What this project is

ModernWigiDash is a .NET 10 WPF application that drives a USB-connected small LCD display (G.Skill WigiDash, VID 0x28DA PID 0xEF01, 1016×592 pixels, RGB565 framebuffer). The application composites customizable widgets (clocks, weather, hardware telemetry, Twitch chat, stock tickers, etc.) onto pages and streams the rendered frames to the display over USB HID/WinUSB.

## Domain Glossary

### Core Concepts

| Term | Definition |
|------|-----------|
| **WigiDash display** | The physical 1016×592 RGB565 LCD connected via USB HID (WinUSB or LibUsbDotNet). Manufactured by G.Skill. |
| **Widget** | A self-contained UI component displayed on the WigiDash canvas. Each widget has a metadata attribute (`[WidgetMetadata]`), renders via SkiaSharp to an `SKCanvas`, and receives touch input. Widgets are registered by reflection and instantiated by `WidgetPluginLoader`. |
| **Page** | A layout container holding placed widgets. The profile holds ordered pages; users swipe between pages at runtime. |
| **PlacedWidgetInstance** | A widget bound to a position on a page — holds coordinates, size, rotation, opacity, and the widget instance. |
| **Profile** | The persisted set of pages, active page index, and widget placements. |
| **Frame** | A pixel buffer (SKBitmap) composited by `SkiaFrameCompositor`, converted to RGB565, and streamed to the display over USB. |
| **FrameSink** | A destination for composited frames. `IFrameSink` exposes `SendFrame(SKBitmap)` + `IsReady`, returning a truthful `FrameDeliveryResult`. The App binds one `FrameDelivery` instance to the direct-USB engine (the WCF sink and `FrameSinkRouter` were removed with the Service, ADR-0005). |
| **FrameDelivery** | The single frame-delivery policy module (Sdk): bounded DropOldest channel → drain-to-latest → paced send, owning encode, an exact-size buffer pool sized from the encoder's output (self-sized by construction — a pool that disagrees with the encoder is unrepresentable), and drop accounting. The send seam returns the truthful `FrameSendResult` (Sent / Refused / Failed), so the delivery's accounting splits a device refusal (`SendRefusedCount` — no live connection, or the frame fails the transport's size contract) from a broken pipe (`SendFailedCount`) — the two no longer share one bool, and both are distinct from drops. One entry point feeds the policy: `Push(SKBitmap)` (encode + pool); a `FrameDelivery.Create` factory makes the required encode/pool/send seams unrepresentable at production bind sites (the ctor remains for tests exercising unconfigured readiness). The App's direct-USB sink is its one runtime instance; pacing defaults to 33ms, the USB engine's device-capability rate. Drop counting lives inside the module. |
| **DisplayGeometry** | The WigiDash framebuffer geometry (Sdk) — the single source of truth for the active pixel area (1016×592, 2 bytes/pixel, payload size). Hardware's `DisplayProtocolConstants` aliases these values and Core's compositor derives its buffer from them, so the pixel area can never drift between projects. |
| **FontCacheEviction** | The font-memoization overflow-bound rule (Core/Rendering): every FontHelper cache keyed by content variety (glyph presence, fallback typeface, text-run splits, cached fonts) is bounded by the same coarse reset — strictly over its own declared cap, clear the whole cache and let it refill on demand (no LRU; every entry recomputes, so an evicted entry costs one recompute). Each cache's cap is declared exactly once in the module (`GlyphPresence`/`FallbackTypeface`/`TextRuns`/`CachedFont` limits), so the four bounded caches can no longer drift from one another or from the tested boundary (`FontCacheEvictionTests` pins the exclusive greater-than boundary and the whole-reset eviction). |
| **IRgb565Encoder / SkiaRgb565Encoder** | The encode seam (Sdk/Hardware): `IRgb565Encoder` exposes `OutputBufferSize` + `Encode(SKBitmap, byte[])` — the delivery pipeline encodes through it, and its output size sizes the delivery's buffer pool; `SkiaRgb565Encoder` is the production adapter over `FrameEncoder`. Tests inject scriptable fakes, so frame delivery is testable without pixels. |
| **ConnectProvider** | One connect attempt in `DisplayHidTransport.Connect`'s provider loop (Hardware): `TryCreate` opens the device and returns the backend (or null when that driver stack cannot provide one). The record carries only the leg's identity — the diagnostic `Tag` (the file-log vocabulary the loop and the leg bind into their `DiagLog` instances, so no line hand-bakes its tag), the display name, and the leg's success line; the loop spells its own position-aware failure lines from the tag, so vocabulary cannot drift between provider and leg. The default list holds the WinUSB provider first and the LibUsbDotNet fallback second; tests inject fakes through the single `ProviderFactories` seam — including a fake LibUsb leg — to drive the connect fallback policy without hardware. The LibUsb leg's device lookup is itself injectable (`LibUsbDeviceProvider`), so its open/config/claim/endpoint teardown is scriptable; every leg failure disposes the LOCAL device, never the adopted global backend (the orphan rule). The connect path's diagnostic vocabulary (leg steps, init sequence, backend failure lines, the engine's connect machine) is one `DiagLog`-bound tag per step/area — no call site composes its own `[TAG]` prefix. |
| **WinUsbApi** | The WinUSB/SetupAPI P/Invoke surface as an injectable delegate bag (Hardware, the PresentMonNative precedent): production binds the real externs once via `WinUsbApi.Default`; tests inject managed fakes, so `WinUsbBulkDevice.Open`'s failure and cleanup paths are scriptable without hardware. |
| **Render tick** | The 30 FPS `DispatcherTimer` in MainWindow that calls `Compositor.Compose()`, converts the frame to RGB565, and queues it for delivery. |

### Hardware / Transport

| Term | Definition |
|------|-----------|
| **Transport** | The USB HID communication layer. `DisplayHidTransport` picks one **ITransferBackend** in `Connect` through the **ConnectProvider** loop — WinUSB (primary) or LibUsbDotNet (fallback) — and runs its connect/init/frame/touch policy against that seam; the init verdict covers the whole sequence including the blank-frame bulk write (on-device, a post-drop reconnect timed out the 1.2 MB init write at the pipe bound while every control write still succeeded — a connected verdict for such a pipe would inherit the falsehood into the engine, so the failed write fails the leg into the existing fallback → Simulated → 5 s reconnect machinery); the backends own the device-specific transfers and teardown (WinUsbBulkDevice implements the seam directly, LibUsbTransferBackend wraps the chunked-write path). `IDisplayTransport` exposes only the live surface the App drives (Connect, SendFrame, ReadTouch, GoToStandby) and every member has a production caller — the transport's own connection truth stays a concrete-class member for test observability, off the seam (the engine's ConnectionState is the production truth). The transport names the worst-case teardown duration behind the engine's never-stall-on-close invariant as `CloseBound` (the max of the WinUSB bulk pipe timeout and the LibUsb chunked-write worst case over a full frame), so the two modules' comments can no longer drift apart. All operations are synchronous — no fake async wrappers. |
| **ITransferBackend** | The transport's USB transfer seam (Hardware): vendor control in/out + bulk write. Two real adapters (WinUSB, LibUsbDotNet) plus test fakes, so the transport's policy is drivable without hardware and the backend choice is made once in `Connect` instead of re-decided per call. |
| **ConnectionState** | The engine's single connection truth (Hardware): `Disconnected` / `Connecting` / `Connected` / `Simulated` — one value instead of the old lockstep IsConnected/IsHardwareActive/IsSimulationMode trio callers disagreed on. The presenter gate and the USB badge read the same state. |
| **DisplayDeviceEngine** | The App's hardware engine (Hardware): owns transport connection, standby, and the 16ms touch poll. The constructor is deliberately inert — no connect attempt, no background loops (construction never reaches for hardware, so test hosts are safe); `Start()` begins the initial connect, the 5s reconnect timer, and touch polling. The connect machine is drivable end-to-end through the transport factory (the internal test ctor wires the factory to the injected transport plus an explicit initial ConnectionState, so even a Start()-triggered reconnect routes through it); the touch loop's failure observer logs instead of going silent. Close never stalls: the standby and dispose close paths wait bounded budgets (`StandbyCloseBudget`, `DisposeAbandonBudget`) that pin to stay strictly shorter than the transport's `CloseBound` worst-case teardown, abandoning a hung device's handle at exit rather than freezing on it. |
| **FramePump** | The 30 FPS presentation cadence module (App): dispatcher timer that composes the active page, hands the frame to the presenter, and requests a repaint — the window keeps only the WPF draw, so the buffer drawn is exactly the buffer sent. Badge refreshes ride the tick as an injected callback. |
| **FrameEncoder** | Converts SKBitmap (RGBA) → RGB565 little-endian byte array for the display's framebuffer format (BGRA/RGBA fast paths + per-pixel fallback, shared `PackRgb565` bit packing; handles scaling when the source bitmap isn't exactly 1016×592). The single bit-packing owner behind the **IRgb565Encoder** seam. |
| **TouchReport** | Hardware touch input from the display: type (Down/Up), X/Y coordinates. Polled by the App's `DisplayDeviceEngine` at 16ms in direct-USB mode and normalized once via the shared `TouchReport.ToEventType` (the single mapping site, also used by the deleted Service seam). The App never sees vendor protocol bytes. |
| **DisplayProtocolConstants** | USB vendor commands, framebuffer dimensions, and protocol constants for the WigiDash hardware. |
| **WinUsbBulkDevice** | Raw WinUSB P/Invoke wrapper for bulk and control transfers. Owned lifecycle (opens SetupAPI handle, initializes WinUSB, manages pipe timeouts). |
| **SystemTelemetryPresentation** | The Hardware Monitor widget's display rules (Widgets): the three unavailable placeholders, the label/unit override resolution, the unknown-mode → Gauge fallback, the clamped invariant-culture hero value, the gauge/bar maximum resolution with its value-derived floor, and the 0..1 progress clamp. The widget's render methods are thin adapters over it — the display is assertable without pixels (its math moved out of the widget with it; the presentation recomputes the value string per Build, so the widget's old per-value format memo is retired). |
| **TrustedUriPolicy** | The shell-open trust rule (Sdk): a host is trusted for the Twitch device-auth browser open only when it IS the twitch.tv apex or a dot-prefixed subdomain — a suffix check would admit attacker-registrable lookalikes (faketwitch.tv). One policy shared by the App's `TrustedBrowserUri` and the Widgets' auto-open guard, so the two sites can never drift. |
| **DisplayFormat** | The display-rules culture contract (Widgets): invariant, zero-aware number formatting (`Fps`/`Ms`/`Pct`/`Count`/`Number`) that every presentation module routes through — one locale contract pinned and tested once instead of per-module interpolation with the ambient culture. |
| **WeatherQueryKey** | The weather cluster's resolution identity (Widgets, ADR-0006): the ONE spelling of "which place was this weather resolved for". `Build(WeatherLocation)` is the only key construction — six identity fields (`LocationType|Location|Latitude|Longitude|CountryCode|LocationMatch`), backslash-escaped, `|`-joined (a separator inside a field can never forge a colliding key; `CustomLabel` is deliberately absent so a label edit never re-fetches); `SameKey` is the only predicate (ordinal, null-safe — case is identity). `KeyPropertyNames` / `InvalidationProperties` / `LocationMatchProperty` declare the field sets once, and `WeatherResolvedIdentity.ResolutionInvalidationProperties` aliases the set so the widget's drift test pins it to the record. Every guard site routes through it — the client's capture window (fetch start + post-save re-validation), the cache-load identity stamp, and the fetch flow's start-key capture + return→apply re-check (`WeatherFetchFlow`, ADR-0007 — the module absorbed the old widget's second inline identity compare with it) — so the stale-identity invariant is assertable in one place, with no pixels and no fetch mocks (`WeatherQueryKeyTests`). |
| **WeatherLocationResolver** | The weather geocoding decision policy (Widgets): candidate ranking/scoring, suffix + diacritic-insensitive matching, population tiebreak, the ambiguity gate, alias tables, ZIP routing, the response-aware weak-ISO fallback (a code match earns the weak bonus only when the state candidate is absent from the response), and the coordinate + label rules (`TryParseCoordinatePair` / `IsValidCoordinate` / `FormatCoordinates`, `ComposeLabel` / `ComposeZipLabel` — moved from the geocoder so the transport owns only HTTP + parse) — the pure decision layer behind `WeatherGeocoder` (a leaf utility `WeatherClient` also calls directly for the forecast URL and ZIP pre-check). Every city-resolution fix commit's rule lives here with its comment. The cluster also uses `Core.Rendering.FontHelper` for the shared font cache, like every other widget. |
| **WeatherClient** | The weather fetch/cache/resolution orchestrator (Widgets): the `WeatherFetchResult` outcome union (each `Fetched`/`Stale` carries the `QueryKey` it was resolved for, so the fetch flow can detect a capture-window identity divergence — `Fetched` is fresh at the completion of the WHOLE capture window, through the cache write: the client re-validates after its save await, so an invalidation landing in the save window converts the verdict to `Stale`), and the explicit-coordinates/ZIP/city/pick resolution legs delegating decisions to `WeatherGeocoder`, plus the snapshot assembly. The fetch-control state machine (5-minute throttle window, single-flight claim, resolved-identity stamp — the mutable twin of the widget's pure `WeatherResolvedIdentity`; both twins hold the shared `WeatherResolutionState` and route their drops through `WeatherInvalidation.Drop`) lives in `WeatherFetchControl`; the cache file mechanics in `WeatherCacheStore`; the response parsing in `WeatherForecastParser`. The display strings never live here (that is the cluster's presentation modules'), and `LoadCacheAsync` documents its state-commitment: a successful load commits the cache's resolved identity + throttle into the fetch-control state, so a caller that DISCARDS the result must roll it back through `InvalidateCoordinates` — the interface says what the load did, so the rejection is the caller's job (the fetch flow enforces the rollback); the flow's own post-await re-validation guards only the return→apply gap the client's window cannot see. The throttle-stamped fact is exposed as the named `HasFetched` predicate (the flow's cadence gate reads it — callers never compare the raw timestamp against `DateTime.MinValue`). |
| **WeatherCacheStore** | The weather cache file module (Widgets): the 1 MB size bound, the lazy name provider, the bounded stat-then-read load with the mid-read-growth guard, the identity stamp (`LocationQueryKey`) each snapshot is saved under, the atomic temp-file save, and `Clear()`. `WeatherClient` owns the staleness decision and applies the returned `WeatherCachePayload` only when the stamp matches the current query key. |
| **WeatherForecastParser** | The Open-Meteo response parser (Widgets): the modern-vs-legacy shape handling (`current` vs `current_weather`, `weather_code` vs `weathercode`), the humidity's current-block provenance (the hourly array's first bucket is stale-by-hours), the invariant day-name formatting with the "Today" marker, and the fetch-limit capping. `WeatherClient` keeps snapshot assembly and calls these pure rules per block. |
| **WeatherForecastLimits** | The fetch-limit constants (Widgets): `MaxFetchDays` / `MaxFetchHours`, the one place the forecast row caps are declared — the parser's strips and the cache store's deserialization both cap through it. |
| **WeatherFetchFlow** | The weather fetch-flow module (Widgets, ADR-0007): the SEQUENCE around one fetch — the identity key captured before the await (through `WeatherQueryKey.Build`), the outcome verification (the `Stale` verdict, then the outcome key vs. start key through `WeatherQueryKey.SameKey` — this gate absorbed the old widget's second inline identity spelling), the post-await live re-check, the drop-and-refetch routing (a dropped result force-refetches the new identity immediately — the in-flight claim that swallowed the edit-time force refresh is released by the completion), the resolved-label write-back gating (the CustomLabel veto + the identity re-check under the host gate — the check + set are one critical section), the single cadence gate (`CanFetch`: the static-snapshot veto once a fetch stamp exists, else the client's throttle window; force always eligible), and the boot-load rollback (a discarded cache load rolls the client's committed identity state back through `InvalidateCoordinates`; a version-only skip leaves nothing to undo). The widget keeps only host concerns — the property coercion (`BuildLocation`), the gate around the display state (the apply and version seams run under the widget's gate), the UI-thread write-back flush, the context requests — and passes them across the typed `IWeatherFetchHost` seam (ADR-0008: the `CurrentLocation` coercion, the gated `TryApply(WeatherApplyRequest)`, the gated write-back queue, the version / static-snapshot / run-token reads, and the two context requests) — the widget IS the production host adapter (explicit implementations; the gate discipline spelled once there) and the flow's tests hold an adapter over the same seam — so `FetchLiveWeatherAsync` / `LoadCachedWeatherAsync` are forwards and the capture-window order (key captured before the await, re-validated after — twice) is enforced in code here, not by comments at a call site. The verdict is assertable at the module interface without a widget instance, a render tick, or the widget's gate (`WeatherFetchFlowTests`). |
| **WeatherFetchFlowOutcome** | The fetch flow's per-fetch verdict union (Widgets): `Applied` / `DroppedStale` / `Skipped` / `Cancelled` — what `WeatherFetchFlow.RunFetchAsync` (the widget's `FetchLiveWeatherAsync` forwards to it) actually did with a fetch's outcome, so the flow is assertable without polling side effects. |
| **WeatherGeocoder** | The geocoding transport layer (Widgets): Open-Meteo/zippopotam HTTP legs with bounded reads and per-leg deadlines, tolerant candidate/ZIP parsing, and the coordinate/ZIP/city entry points — delegating every ranking/decision rule to `WeatherLocationResolver` (a leaf utility the client also calls directly for the forecast URL and ZIP pre-check). |
| **WeatherFetchResult** | The fetch-outcome union (Widgets): `Fetched`/`Throttled`/`InFlight`/`Failed`/`Stale` — a fetch result without a snapshot is unrepresentable; the fetch flow distinguishes "try again now" (`Stale`) from "keep what you have" (the rest). |
| **WeatherInvalidation** | The resolved-identity invalidation rule (Widgets): the ONE property → drop-granularity map (`KindForProperty`: the `LocationMatch` pick → `Coordinates`, every other resolution input → `Location`, display-only properties → `None`) that the widget's `OnPropertyChanged` routes every resolution-input edit through, so the client's fetch-control twin and the widget's resolved-identity twin can never drift on what an edit drops — `Coordinates` voids the resolved name/population (the widget twin's pending label write-back included, the client twin's identity query + throttle reset) but KEEPS the geocode candidates on both twins (a pick resolves against the candidates it was offered from); `Location` voids the WHOLE identity (candidates included) on both twins. The identity value itself is the shared `WeatherResolutionState` record (candidates, resolved name, population) both twins hold, and the single drop rule `Drop(kind, state)` applies the declared granularity to that value (None is the identity function; Coordinates drops name + population and KEEPS the candidates; Location empties it to the one `Empty` state) — the twins' transitions route their shared part through it, then clear their OWN unique fields (the client's coordinates + query + throttle, the widget's pending write-back). The twin-equivalence pin drives both twins through every kind and compares their resulting identity values structurally (plus the pure `Drop` pins per kind), so a new resolved field added to the record is caught the moment a twin's transition forgets to route it through the rule (`WeatherInvalidationTests`). |
| **WeatherResolutionState** | The shared resolved-identity value (Widgets): the geocode candidates, the resolved header city name, and the resolved population, as ONE record — the value both invalidation twins hold (the client's fetch-control state machine and the widget's resolved-identity module). Declared once; dropped by the single rule `WeatherInvalidation.Drop`; the twins add their unique fields around it (coordinates + identity query + throttle on the client, the pending label write-back on the widget) and route their drops through the rule, so the shared part of what an edit drops can never drift between them. The null-keeps `With` is the "response omitted this section — keep the previous value" replacement rule; the one static `Empty` is the drop destination both twins land on. |
| **WidgetRouting** | The page-input routing module (Core): hit-test + touch routing over a page's placed widgets (rotated-local coordinates, highest-ZIndex selection) — extracted from the compositor so the renderer owns only rendering + edit state. |
| **TwitchChatStatusPolicy** | The Twitch chat's connection/buffer policy (Widgets): the IRC NOTICE→connection-state transition and the message-buffer cap — split from `TwitchChatPresentation` (display strings only). |
| **WidgetCreateResult** | The widget-creation outcome (Core): `Ok(widget)` / `NotFound` / `Broken(reason)` — a broken plugin is distinguishable from an absent one (the old null-or-null ambiguity), and `PluginInfo` is an immutable record. |

### Service Architecture

> historical context; the repo no longer contains a Service project, a WCF
> contract/client, or any service-routing machinery.

| Term | Definition |
|------|-----------|
| **Service** | ~~A Windows Service (`ModernWigiDashService`) running as LocalSystem that owns the USB device, captures telemetry, and exposes a WCF endpoint.~~ **Removed (ADR-0005)**: its frame-time role lives in PresentMon Service, its sensor role in LibreHardwareService, and the app talks USB directly. |
| **Service.Contracts** | ~~Shared assembly with the WCF contract and client.~~ **Removed (ADR-0005)** — its live telemetry DTOs (`SensorSnapshotDto`, `SensorReadingDto`, `FrameTimeSnapshotDto`) moved into `ModernWigiDash.Sdk` as plain data models. |
| **DetectServicePort** | ~~Protocol-verified service discovery.~~ Removed with the service (ADR-0005). |
| **ServiceRoutingState** | ~~Owns the App↔service routing truth.~~ Removed with the service (ADR-0005); poll loops are all direct producers now. |
| **ProfileOps** | The pure profile-operations module (Core): page CRUD, widget placement/rehydration (`PlaceWidget`, `PlaceCentered` — the centered variant reads the catalog entry's nominal default size, the widget's [WidgetMetadata] fact, so it never constructs a probe instance), the bounds-safe `TryGetPage` accessor (the window's delete confirm reads the page's confirm facts through it, so a stale index is a silent no-op in the window, never a throw ahead of `DeletePage`'s own validation), and JSON export/import (the import delegates untrusted-input sanitization to `ProfileImportSanitizer`). MainWindow keeps only dialogs, selection, and refresh — the user-visible model mutations are testable through the module's interface. |
| **ProfileImportSanitizer** | The untrusted-import sanitization (Core/Models): the caps and value rules every foreign profile passes before rehydration — the page/widget-count DoS caps, the null/empty collection repair (pages, page elements, `-widgets`, `propertyValues`), the page-background and widget image/icon paths restricted to safe relative paths (rooted/UNC/drive-relative/`..` rejected), the unconditional ActionCommand clear (Process.Start/SendInput), the IRC-channel sanitization via `TwitchChannelRule`, the InstanceId regenerate-or-dedup rule (its `IsSafeInstanceId` is also the weather widget's defense-in-depth cache-file-key guard), and the string-value bound. The import file-size guard (`MaxImportFileBytes` + `IsImportFileTooLarge`) lives with the rules it protects; `ProfileOps.ImportJson` is the sole caller and the app's own persisted profile passes with `sanitize: false`. |
| **ProfileMutationShape** | The window's one post-mutation contract (App): `MainWindow.ApplyProfileMutation(shape, selection)` is the single entry every profile mutation routes through after it lands. The `shape` selects the refresh bundle — `Transform` (in-page state only: place/remove/clear, transform/opacity write-backs, snap-to-grid, page background) re-syncs nothing structural; `Structural` (add/delete/rename/switch page) re-syncs the tab strip + page-background picker; `RawWrite` (an import) does both plus re-syncs the snap-to-grid toggle from the imported page (absorbing the import's old direct control write). Every shape then re-applies the selection, refreshes the active count, repaints the canvas, and marks the profile dirty exactly once — so no call site re-derives "what happens after a mutation" and the old doubled/missing marks are unrepresentable. Inspector-driven write-backs are the one path that marks through the controller's `onProfileChanged` callback instead (one invocation per landed write-back; the window's forwarding handlers add none). `SelectWidget`'s same-reference early-out keeps the idempotent re-entry on the import path from re-applying a disposed selected instance. |
| **PollLoop** | One parameterized poll loop (Sdk): owns its cancellation lifecycle, readiness guard, failure logging, and inter-tick delay. The App's two direct producers (sensor 1s, frame-time 1s) and the engine's direct-USB touch loop (16ms) are all instances with injected probes and sample sinks — one loop shape, every hop. |
| **Standby** | The display's idle state: the built-in vendor Welcome screen. Entered on the app-close path — the engine's `Dispose` sends `GoToStandby`. After standby, heartbeats stop, so the display also sleeps on its own timeout. |

### Telemetry & Data Flow

| Term | Definition |
|------|-----------|
| **LhmSensorStore** | Static in-process cache of hardware sensor readings from LibreHardwareService. A facade over `TelemetryStoreFacade<SensorSnapshotDto>` (Sdk) — the snapshot shape is the DTO itself (no shadow record); the reading label (`HardwareName: SensorName`) derives as a computed property on the DTO, the single derivation site the picker and widgets share. Written by the App's shared-memory producer (`LhmSharedMemoryReader` → `UpdateFromDto`, producer timestamp preserved); read by `HardwareMonitorWidget` through `TryReadFresh` — the store owns the staleness decision, consumers cannot skip it. |
| **ILhmMapSource** | The named-map I/O seam behind the LHS reader (Hardware/App): one mutex-guarded, bounded copy of the sensors map, or null with an error. The real adapter (`MemoryMappedLhmMapSource`) owns the MemoryMappedFile/Mutex specifics and the attacker-claimed-size copy caps; in-memory fakes drive the reader's Poll policy in tests. |
| **FrameTimeStore** | Static in-process cache of FPS/frame-time snapshots. A facade over `TelemetryStoreFacade<FrameTimeSnapshotDto>` (Sdk) with the same shape as `LhmSensorStore` — the snapshot shape is the DTO itself (no shadow record). Written by the PresentMon producer (see below) via `FrameTimeStore.UpdateFromDto` (producer timestamp preserved); read by `FrameTimeWidget` through `TryReadFresh`. The widget renders only PresentMon-reported data: an 8-metric dashboard view (FPS/frame time hero, 1% low, 0.1% low, CPU frame, GPU busy %, displayed FPS, dropped frames, GPU time, present mode) that tap-toggles to a PresentMon-overlay-style readout; both views shrink gracefully and show zero values when no process is tracked (PresentMon's own 0-presents reading; no monitor-refresh-rate display — that is not a PresentMon feature) **and when the tracked target is not actually displayed** — the producer's target-trust policy (`TargetTrustPolicy`: settling window, adoption, frozen-data guard) reports live data only for the pid that produced the last live sample: on a foreground switch it holds the zero state through a settling window (PresentMon returns the departed target's frozen data for every pid after a switch — observed on-device), an adopted target's data is only reported once it differs from the departed target's last values, and a presenting-but-not-displayed target (backgrounded fullscreen game, `PM_METRIC_DISPLAYED_FPS` = 0) also reads as the idle zero state. |
| **TelemetryStoreFacade** | The store-facade shape (Sdk): owns one `TelemetryStore<TRecord>` instance bound to the domain's empty value and staleness window, and adds the null-tolerant producer write plus the fake-clock test seams. `LhmSensorStore` and `FrameTimeStore` wrap one instance each — the staleness policy and its test surface are declared exactly once (the former `StaticTelemetryStore` pass-through layer was folded into the facade). |
| **PresentMon producer** | The frame-time source (ADR-0003). Replaces the deleted `FrameTimeReader`: the app connects to PresentMon Service (`pmOpenSession`, non-elevated), resolves a target PID (preferred foreground window, else most-active presenter), calls `pmStartTrackingProcess`, and polls a rolling 1s dynamic query (`PM_METRIC_PRESENTED_FPS` AVG/P99/P01, `CPU_FRAME_TIME`, `GPU_TIME`, `GPU_BUSY`, `DISPLAYED_FPS`, `DROPPED_FRAMES`, `PRESENT_MODE`, `APPLICATION`) on the existing 1s `PollLoop` shape. Results map into `FrameTimeSnapshotDto` → `FrameTimeStore.Update`. Loads `PresentMonAPI2.dll` from the service SDK dir at runtime — never ships its own copy (client↔service binary protocol isn't backward-guaranteed, issue #383). Absent service ⇒ widget shows a graceful "PresentMon not installed" state. |
| **PresentMonMetricCatalog** | The installed service's metric truth (App/PresentMon): built once per session from `pmGetIntrospectionRoot`, it exposes each metric's type/unit and the stats the service accepts. `PresentMonQueryBuilder` builds the dynamic query from wanted specs against the catalog — an unsupported metric degrades to a named drop (the field reads no-data) instead of an opaque QueryMalformed failure, and a rejected preferred stat falls back to the first allowed one (PRESENT_MODE only accepts NEWEST_POINT/MID_LERP). |
| **PresentMonQueryRegistry** | The query subsystem (App/PresentMon): registers the dynamic + frame queries, owns the elements, the field→element map, the blob strides, and the poll/drain loops (capacity growth, bounded drain). Pure policy over injected delegates, so the loops are unit-testable without the DLL; `PresentMonNative` keeps only the session and tracking surface. Enum-typed metrics (PRESENT_MODE) are read as 4-byte int32 per the element's DataSize, not as doubles. |
| **FrameTimeSnapshotFactory** | The only place the frame-time snapshot gets shaped (App/PresentMon): unavailable/idle/capture-dead outcomes and the live mapping with its unit conversions (1000/FPS frame time, GPU busy ms → busy-per-frame %). Extracted from the producer's poll method so the conversions are directly testable. |
| **FrameTimePresentation** | The widget's display rules (Widgets): given a snapshot and placement size, the hero strings, the eight dashboard cards, the nine overlay rows (PresentMon's metric names; 1000/percentile-fps frame times), and the shrink visibility flags. The widget's render methods are thin adapters over it — the display is assertable without pixels. |

### Data Flow

1. **Render loop**: MainWindow tick → `SkiaFrameCompositor.Compose()` → `FrameDelivery` (encode + pool + pace) → `DisplayDeviceEngine.SendFrameBytes()` → `IDisplayTransport.SendFrame()`
2. **Touch flow**: `DisplayDeviceEngine.TouchPollTick` (16ms PollLoop, reads `ReadTouch()`, normalizes raw byte → `TouchEventType` via `TouchReport.ToEventType`) → `OnTouchEvent` → MainWindow → `SkiaFrameCompositor.RouteTouch()` → `IModernWidget.OnTouch()`
3. **Sensor flow**: `LhmSharedMemoryReader` (App, reads LibreHardwareService shared memory on the 1s `PollLoop` shape) → `LhmSensorStore.UpdateFromDto()` (static cache) → `HardwareMonitorWidget.Render()` reads snapshot
4. **Frame-time flow**: PresentMon producer (ADR-0003: `pmOpenSession` → `pmStartTrackingProcess(pid)` → dynamic-query poll on the 1s `PollLoop` shape) → `FrameTimeStore.Update()` (static cache) → `FrameTimeWidget.Render()` reads snapshot

### Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Synchronous transport interface | USB I/O (WinUSB/LibUsbDotNet) is inherently blocking; fake async adds no value and forces sync-over-async bridges |
| Static stores with LastUpdate freshness | Widgets are instantiated via reflection (parameterless ctor) and can't receive injected dependencies; static stores with staleness tracking are the pragmatic solution |
| Telemetry DTOs in Sdk | `SensorSnapshotDto`/`SensorReadingDto`/`FrameTimeSnapshotDto` live in the lowest common layer so every project shares one mailbox format (the Service.Contracts assembly was removed with the service, ADR-0005) |
| FileLog in Sdk | Shared file logging utility placed in the lowest common layer so all projects can log to `display_device.log` without circular dependencies |
| Widget-per-file convention | Each widget class lives in its own `.cs` file with its `[WidgetMetadata]` attribute; the catalog is discovered by scanning the assembly. One type per file also holds for the Sdk contract — `IModernWidget`, `ModernWidgetBase`, and `IWidgetActionInvoker` each own one file (split out of the former single `IModernWidget.cs`) |

## Architecture Decisions

| ADR | Decision | Rationale |
|-----|----------|-----------|
| [ADR-0001](docs/adr/0001-synchronous-transport-interface.md) | Synchronous transport interface | USB I/O is inherently blocking; fake async adds cognitive overhead and prevents compile-time detection of sync-over-async |
| [ADR-0002](docs/adr/0002-named-pipe-wcf-transport.md) | ~~Named-pipe WCF transport~~ **Superseded by ADR-0005** | The WCF pipe is gone with the Service (ADR-0005); kept for history |
| [ADR-0003](docs/adr/0003-presentmon-service-for-frame-time.md) | PresentMon Service as frame-time source | Replaces the in-house ETW reader; Intel's LocalSystem service + named-pipe client matches the non-elevation goal with no custom ETW capture to maintain |
| [ADR-0004](docs/adr/0004-librehardwareservice-shared-memory-for-sensors.md) | LibreHardwareService shared memory as hardware sensor source | Replaces the in-house WCF sensor reader; LHS's LocalSystem service + mutex-guarded shared-memory maps match the non-elevation and low-overhead goals with no custom hardware-polling code to maintain |
| [ADR-0005](docs/adr/0005-remove-windows-service.md) | Remove the ModernWigiDash Windows Service | Once telemetry came from PresentMon/LibreHardwareService and the app owned the USB device directly, the Service and its WCF pipe were dead weight — a whole project, a named-pipe attack surface, and install machinery to maintain |
| [ADR-0006](docs/adr/0006-stale-identity-invariant.md) | One owner of the weather stale-identity invariant (`WeatherQueryKey`) | The rule "never apply weather resolved for a different place than the UI shows" was spelled 4+ ways (client capture window, cache-load stamp compare, widget return→apply re-check) and held by comments alone with no test surface — `WeatherQueryKey.Build` is the only key construction and `SameKey` the only predicate, so every guard site routes through one owner with a direct test surface |
| [ADR-0007](docs/adr/0007-weather-fetch-flow-module.md) | One fetch-flow module owns the weather fetch sequence (`WeatherFetchFlow`) | The capture window, the two drop gates, the drop-and-refetch routing, the write-back gating, the cadence gate, and the boot-load rollback were spelled across five widget methods, held by comments, and testable only through a live widget; the module enforces the sequence in code and exposes it as one interface (`CanFetch` / `RunFetchAsync` / `RunBootLoadAsync`) the widget forwards to, so the ADR-0006 predicate absorbs the old widget's second inline identity compare and the whole flow is pinned without a widget, a render tick, or the widget's gate |
| [ADR-0008](docs/adr/0008-typed-weather-fetch-host-seam.md) | The weather fetch flow's host seam is typed (`IWeatherFetchHost` + `WeatherApplyRequest`) | ADR-0007's own Negative — the ten-delegate bag was a discipline, not a type: a named seam gives the host contract a single spelling (and a test-double surface) and the apply payload a name, so a new payload field is a named addition to the record instead of a seven-positional-argument signature change on both sides |
